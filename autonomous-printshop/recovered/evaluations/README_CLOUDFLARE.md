# إعداد Cloudflare المستقل — برنامج تقييمات مطبعجي V4

**حالة هذا المسار: PILOT / لم يُنشَر بعد.** استخدام حساب Cloudflare المدفوع الموجود لدى المالك مع **موارد جديدة مستقلة** فقط. هذا المسار لا يستخدم ولا يُعدّل `trendos-main` أو أي Worker/Binding/Route/Script/Google Sheet يخص TrendOS.

## ما الجاهز فعليًا؟

- `src/worker.mjs`: API تجريبي منفصل، مغلق افتراضيًا حتى توصيل `MATBAGY_ADMIN_TOKEN` و`EVAL_DB` و`EVAL_FILES`.
- `migrations/0001_evaluations.sql`: جداول العملاء والموظفين، نسخ المحادثات، الرسائل، بصمة التعامل، مسودات الرد، الأوامر وسجل المراجعة.
- `wrangler.example.toml`: **قالب** لتكوين Worker باسم جديد وBinding وD1/R2 جديدة. قيمة DB ID فيه placeholder وليس DB قائمة.
- `tests/pilot.test.mjs`: اختبارات محلية للغلق الافتراضي، ومقاومة الدخول غير المصرح، وقبول TXT تجريبي.

**البرنامج المحلي Python/V4 هو النسخة الأوسع للتجربة الآن.** Worker الحالي نواة API مستقلة فقط: رفع TXT بحد 1MB و80 رسالة في الدفعة، وإنشاء عميل، وإنشاء ملاحظة ومراجعتها، وإضافة أمر انتظار. لا توجد فيه واجهة Dashboard كاملة، ولا دعم ZIP/صوت/صورة، ولا API لتحليل AI، ولا توافق تلقائي بين قاعدة SQLite المحلية وD1. عدم اكتمال السحابة لا يعطل اختبار البرنامج محليًا.

## نشر أولي مقيد الصلاحيات — ينفذه مسؤول IT بعد اعتماد الحساب والموارد

1. أنشئ **مستودع GitHub خاصًا جديدًا** للتقييمات من غير ملفات عملاء، وارفع محتوى الحزمة بعد مراجعة `git status` و`git diff --cached --name-only`. لا ترفع المستودع إلى TrendOS.
2. افتح حساب Cloudflare المناسب وتأكد من صلاحيات Workers وD1 وR2 ومن طريقة حماية الوصول. أنشئ **D1 جديدة باسم مختلف** وR2 bucket خاصًا مستقلًا. لا تنسخ أي معرّف أو مفتاح أو Worker binding تابع لترند.
3. انسخ `wrangler.example.toml` إلى `wrangler.toml` محليًا. ضع **معرّف D1 الجديدة فقط** بدل placeholder، وتحقق أن Worker/bucket/database لا تطابق أي مورد إنتاجي. لا تضف معرّفات أو Tokens حقيقية للكتاب أو GitHub.
4. اترك `workers_dev=false` في القالب وقت إعداد الموارد والمراجعة الأولى حتى لا ينفتح عنوان عام بالخطأ.
5. راجع المهاجرة `0001_evaluations.sql` وطبّقها **على D1 الجديدة فقط** بعد التأكد من اسم القاعدة والهدف. لا تُشغّل migrations باسم عام أو على موارد الإنتاج. أنشئ سرّ Worker منفصلًا باسم `MATBAGY_ADMIN_TOKEN` من Secrets (ليس Variables عامة ولا frontend).
6. قبل السماح برفع بيانات عملاء، فعّل **Cloudflare Access على Worker كله** مع السماح لحسابات المسؤولين المخولين فقط. لا تعتمد على حجب رابط الواجهة أو على Bearer token واحد كحماية إنتاجية كافية. احمِ أيضًا preview/version URLs وراجع سياسة الدخول عمليًا. توثيق Cloudflare: https://developers.cloudflare.com/workers/configuration/cloudflare-access/
7. بعد تثبيت Access واختبار قواعده، فعّل مسار وصول مستقلًا مقيدًا بالسياسة؛ لا تفعّل عنوان Worker عام قبل إعداد الحماية. اختبر من خارج الجلسة أن كل `/api/*` يرفض الاتصال غير المصرح، وأن الموارد المعروضة في Settings هي **EVAL_DB / EVAL_FILES الجديدتان فقط**. اختبر باستخدام TXT وهمي قصير، ثم راجع وجود الرسائل في D1 والملف في R2 والتمييز بين إعادة الاستيراد والتكرار.
8. اضبط نسخ D1/R2 الاحتياطية ومراجعة صلاحيات الوصول وسياسة احتفاظ وحذف مستندات العملاء واختبار استعادة فعلي. لا تبدأ رفع محادثات حقيقية قبل توثيق الموافقة وسياسة الاحتفاظ والوصول.

### أوامر مرجعية للـIT فقط — لا تشغّلها على موارد ترند

```sh
# بعد تسجيل الدخول والمراجعة اليدوية للحساب المقصود:
npx wrangler d1 create matbagy-evaluations-pilot
npx wrangler r2 bucket create matbagy-evaluations-private
cp wrangler.example.toml wrangler.toml
# الصق DB ID التي أُنشئت الآن في wrangler.toml المحلي فقط.
npx wrangler d1 migrations apply matbagy-evaluations-pilot --remote
npx wrangler secret put MATBAGY_ADMIN_TOKEN
npx wrangler deploy
```

**تحذير:** الأوامر أعلاه تنشئ وتغيّر موارد Cloudflare فعلية. لا تنفذها قبل مراجعة الحساب والصلاحيات واسم وDB ID الموارد الجديدة وتفعيل حماية Access؛ لم تُنفذ أثناء إعداد الحزمة. إذا كانت R2 غير مفعّلة في الحساب، يلزم مراجعة شروط التفعيل والتكلفة قبل الإنشاء، ولا يُفترض أنها داخلة تلقائيًا في مبلغ Workers Paid.

## واجهات API التجريبية

- `GET /health` عام ويعرض اسم الخدمة وحقيقة عدم الربط بترند فقط.
- `GET /api/customers` و`POST /api/customers` بعد مصادقة المسؤول.
- `POST /api/exports/txt` مع `Content-Type: text/plain` و`X-Customer-Id`, `X-Source-Id` لجلب TXT **بصيغة التاريخ يوم/شهر/سنة**؛ الملف يُخزن في R2 والرسائل في D1.
- `GET /api/customers/:id/fingerprint` لا يعرض إلا الوقائع المعتمدة.
- `POST /api/profile/facts`, `POST /api/profile/facts/:id/review` لحفظ الواقعة مع أدلتها ومراجعتها.
- `POST /api/actions` يضيف اقتراحًا إلى قائمة انتظار فقط: `external_write=false`.

**فارق مرجع الدليل:** في SQLite المحلي يكون مثل `private/main#12`، وفي Worker السحابي مثل `private/main#<24 hex>`؛ يلزم تصميم ترحيل يطابقهما بالدليل الأصلي قبل نقل بيانات حقيقية، ولا يُنقل الرقم المحلي مباشرةً.

## الفجوات قبل إطلاق النسخة الكاملة

لوحة مستخدمين محمية بأدوار، API لكل وظائف بصمة الموظف ومسودات الرد، رفع دفعات كبيرة وZIP/فويسات/صور، اتصال واتساب مصرح به، ترحيل بيانات محلية مثبت ومقارن، اختبارات E2E على موارد TEST منفصلة، مراقبة التكلفة، وخطة حذف/استعادة. **النشر التجريبي لملفات هذا المجلد وحده ليس إطلاقًا جاهزًا لمحادثات العملاء الحقيقية.**

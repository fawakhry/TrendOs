# AP-301 — إعداد حساب قراءة متعدد الأقسام لسيرفر TrendosShop (بدون إنشاء حساب حي)

**موافقة المالك بتاريخ 2026-10-16:** تجهيز تصميم حساب خدمة مستقل وإعداد طريقة الربط على GitHub، بصلاحية قراءة أوردرات **الطباعة والليزر فقط**، قابل للتوسع لاحقًا بعد موافقة مستقلة. الموافقة **لا تشمل** إنشاء/تفعيل مستخدم إنتاجي، قراءة أوردرات عملاء، أو استخدام Secret حي.

## القرار المعماري

- **اسم تعريف مقترح فقط:** `trendosshop_order_reader`. ليس مستخدمًا موجودًا في قاعدة البيانات ولم تُنشأ كلمة مرور أو Token.
- **نوع الحساب المقترح:** حساب خدمة مخصص للاتصال من Ubuntu، وليس حساب ضياء/مدير ولا موظف عادي بامتيازات إدارية. دعم هذا النوع/الدور داخل Backend ما زال **غير مثبت**.
- **الصلاحيات المطلوبة:** قراءة أوردرات شاشتي `print` و`laser` فقط، أي قسم `طباعة` أو `ليزر`؛ عملية منطقية واحدة `orders.read`، مع إمكانية توسيعها لخدمات مسجلة ومعتمدة لاحقًا (ليس تلقائيًا).
- **الصلاحيات الممنوعة:** تعديل أو حذف أو إنشاء أوردرات، تغيير حالة بند، قراءة أو تعديل الحسابات أو المخزون، إدارة الموظفين، قائمة العملاء العامة، التحكم في الطابعات/الماكينات، إجراءات المطابقة المالية أو إنشاء مفاتيح دخول إضافية.
- **أوردر متعدد الأقسام:** `orderId` موحد، و`lineId` لكل بند/قسم. لا تعتبر حالة قسم واحد إكمالًا للأوردر كله.
- **مبدأ الأمان:** Backend صاحب سلطة تحديد الصلاحيات. ملف إعدادات Ubuntu أو فلتر `screen` في الواجهة **لا** يمنح صلاحية أو يثبت منع الكتابة.

## الموجود في الكود الجديد (بيانات وهمية فقط)

- `src/trendos_service_identity_plan.py` يفحص نموذج منح صلاحيات اصطناعيًا، ويرفض زيادة شاشات أو أفعال القراءة المسموحة، أو إضافة `service/press` أو أعمال كتابة، أو توكنات وبيانات حساسة ضمن النموذج.
- يعتمد على `AP-299` في حصر الخدمات المسموح بها. إضافة خدمة أخرى تتطلب تسجيلًا واضحًا وسياسة مؤهلة، ولا تمنح الوصول تلقائيًا.
- لا يستورد GitHub Secrets أو ملف إعدادات إنتاجي، ولا يفتح شبكة، ولا يصدر هوية أو Token أو يعدل ملفات الجهاز.
- لا يُرجع صلاحية إطلاق في أي ظرف: `realBackendRoleExistsVerified=false` و`productionAuthorizationAllowed=false`. **الاختبارات تثبت سياسة مطلوبة فقط ولا تثبت تطبيقها الحقيقي.**

## حدود النسخة الحية المؤكدة وغير المؤكدة

1. كود Frontend الافتراضي يستخدم `/v1/edge/orders/session` ثم `/v1/edge/orders/02cr/page`، لكن لم يجر إثبات أي Backend منشور متوافق مع صلاحيات `print+laser` فقط.
2. نسخة Worker تاريخية مفحوصة لديها صلاحيات `admin` و`print` و`laser` منفصلة؛ `print` يشمل `press` وشاشة فارغة. لا يوجد في هذا المصدر دور جاهز `trendosshop_order_reader` متعدد الأقسام مع منع الكتابة. يلزم تأهيل أو إضافة صلاحيات حقيقية جهة السيرفر **بقرار منفصل**.
3. الـSecrets الموجودة في GitHub باسم `TRENDOS_PROD_QUALIFY_...` تُترك دون تغيير؛ ما ظهر من توثيق تاريخي يشير إلى `401 / Session miss`. لا تستخدم حساب ضياء لربط المطبعة.
4. `TrendosShop` ما زال في البيت والنسخة المحلية `a238ce5a...` (عند آخر صورة). لا تفترض وصوله للماكينات أو أنه مرتبط فعليًا بالمنصة.

## خطوات التأهيل المتبقية

**G1 — تدقيق دور وواجهات الـAPI الفعلية:** تحديد Backend المنشور وصفحات `print/laser` وتأكيد server-side department filtering والقراءة فقط والاستجابة والصلاحية العابرة للأقسام. لا تبدأ بتعديل Production.

**G2 — بوابة إنشاء الحساب:** بعد إثبات دعم الصلاحيات، إعداد سياسة إنشاء مستخدم خدمة مستقل ومدة جلسة قصيرة وآلية تدوير مفاتيح وسحبها وإيقافها وفصلها عن حسابات الموظفين، ثم **الحصول على تفويض صريح إضافي** قبل أي تغيير حي.

**G3 — وسيلة تخزين الأسرار:** استخدام مخزن مفاتيح مناسب للبيئة. لا تُنسخ القيم في محادثات ChatGPT أو مستودع GitHub أو سجلات CI، ولا تُنقل تلقائيًا إلى Ubuntu. التحقق من قدرة الحساب وحدوده بدون إخراج قيمة التوكن.

**G4 — عميل ربط one-shot منفصل:** فقط بعد G1/G2، مراجعة HTTPS صادر إلى Host ثابت مع TLS موثوق ورفض Redirect وحدود حجم/زمن؛ ممنوع ربطه بـ `run.py` أو background bridge أو السماح بكتابة ملفات محلية أو حالات أوردرات.

**G5 — اختبار حي منفصل:** اختبار مصادق عليه لأوردرات القسمين بحد أدنى من الصلاحيات وقراءة واحدة محدودة بعد تفويض المالك، ثم تسجيل نتيجة Audit قابلة للإيقاف والتراجع، بدون أوردرات حساسة في Logs.

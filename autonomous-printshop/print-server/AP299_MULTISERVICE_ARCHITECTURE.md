# AP-299 — القرار المعماري: برنامج متعدد الأقسام والخدمات

**قرار المالك بتاريخ 2026-10-16:** البرنامج ليس للطباعة فقط. النواة تدير **الطباعة + الليزر**، وتقبل إضافة خدمات وأقسام أخرى مستقبلًا بدون نسخ مشروع جديد لكل قسم. قد يتكوّن الأوردر الواحد من بنود تنفذها أقسام مختلفة.

## تصحيح سوء الفهم

- **AP-298** فحص خصوصية/صلاحيات وهمي لقسم الطباعة فقط؛ يبقى كاختبار منع الوصول الزائد ولا يُستخدم معيارًا يحدد نطاق المنتج أو يرفض وجود الليزر بالنظام.
- **AP-299** يقدم فحصًا تجريبيًا متعدد الأقسام، ويحتفظ بكل وظيفة فعالة من AP-296 وAP-298. هذا ليس التشغيل الفعلي أو بناء الواجهة الكاملة.
- فصل **خدمة العمل** مثل فوتو/سبلميشن/كوشيه/ليزر عن **القسم أو شاشة القراءة** وعن **صلاحيات موظف**. وجود كلمة «طباعة» في اسم المشروع لا يغيّر حقائق التصنيف.

## النموذج المستهدف

```text
TrendOS — أوردر مركزي واحد
  ├─ بند 1 — قسم طباعة — مهمة/ملفات/اعتماد/متابعة
  ├─ بند 2 — قسم ليزر  — مهمة/ملفات/اعتماد/متابعة
  └─ بند 3 — خدمة مستقبلية معتمدة — مهمة مستقلة
               ↓
Print Server متعدد الخدمات + موظفون/إيجنتات بحسب صلاحياتهم
               ↓
حالة إجمالية للأوردر لا تعتبر منتهية قبل اكتمال كل بنوده المؤهلة
```

أول مرحلتين مستهدفتين هما `print → طباعة` و`laser → ليزر`. أقسام أخرى مثل السبلميشن/المكبس والخدمات الجديدة تحتاج اختيار طريقة تمثيلها بالـAPI الموجود وتحديد الأقسام/المهام وتفويض مستقل، ولا نفترض أنها موجودة بالفعل.

## ما نُفّذ على GitHub

- `src/trendos_service_scope_gate.py`: سجل خدمات ابتدائي للطباعة والليزر؛ يمكن إضافة خدمة جديدة بــ `ServiceSpec(code, screen, department)` من سجل محلي معتمد؛ لا يقبل أي قيمة خدمة أو قسم من بيانات أوردر كتصريح ذاتي.
- يقبل فقط **grant تجريبي** مطابقًا بالضبط لشاشات الخدمات المفعّلة، ويستبعد الحسابات الإدارية والأقسام الأخرى.
- يعيد استخدام `src/trendos_shadow_qualifier.py` (AP-296) مرة لكل شاشة في الذاكرة فقط؛ يحسب البنود وأعداد الأوردرات الفريدة دون إخراج أرقام الأوردرات نفسها. الأوردر الموزع على الطباعة والليزر يظل أوردرًا واحدًا في إجمالي العداد.
- يرفض أن تستخدم الشاشة الواحدة قسمين مختلفين بدون عقد فصل حقيقي؛ الزيادة لــ screen جديدة تحتاج تأهيل API وAP-296 وليس اسمًا جديدًا فقط.
- الاختبارات لا تشغل سيرفرًا، ولا تنادي الإنترنت، ولا تستخدم Secrets أو بيانات عملاء، ولا ترسل طباعة أو تعدّل حالة إنتاج.

## تطوير لاحق مستقل — ليس ادعاء تنفيذ

1. **سجل خدمات إداري فعلي** مع تفعيل/تعطيل الخدمة، القسم، المعدات المؤهلة، قواعد الملفات، ومراحل التنفيذ.
2. **عقد أوردر وبنود متعدد الأقسام** يُبقي `orderId` مرجعًا واحدًا ويعطي كل بند `lineId` ومسار تشغيل محددًا.
3. **صلاحيات مستقلة**: المشرف يرى الأقسام المصرح بها؛ الموظف ينفذ المهام المؤهلة فقط؛ الإيجنت يقرأ/يقترح وينفذ العمليات المصرح بها حسب فئة القرار. تعدد الأقسام لا يعني صلاحيات عامة.
4. **مصدر TrendOS الحي**: إثبات endpoint منشور فعليًا ودليل تفويض السيرفر للقراءة فقط؛ اختلاف `getRows` و`getRowsPageV1931` ومسارات Edge ما زال غير محسوم.
5. **تأهيل أجهزة المطبعة**: سيرفر `TrendosShop` ما زال في البيت؛ لا تشغيل طابعات أو ملامسة ملفات Windows 7 أو Cloudflare/D1/EasyStore بدون موافقة.
6. **إضافة خدمة** تمر بمراجعة التصنيف وصلاحيات API والبيانات والاختبارات قبل التفعيل (OFF → SHADOW → CANARY → AUTO حسب الصلاحيات).

## درجة الإثبات

`AP299_DESIGN_OWNER_APPROVED=YES` (التصحيح الصريح من المالك).  
`AP299_LOCAL_MULTI_DEPT_FIXTURE=SOURCE_ONLY`; `AP299_LIVE_API=UNVERIFIED`.  
`AP299_PR=OPEN_DRAFT`; `UBUNTU_CODE_UPDATED=NO`; `PRODUCTION_PRINTING=OFF`.  
حتى بعد PASS لجميع الاختبارات، لا يُعتبر هذا تطوير كل وحدات المطبعة المطلوبة أو إذنًا بتشغيل خدمات حية.

# AP-300 — تأهيل عقد قراءة أوردرات الطباعة والليزر (مراجعة مصدر فقط)

**التاريخ:** 2026-10-16. **الحالة:** `SOURCE_AUDIT / LIVE_NO_GO`.  
**المصدر:** المستودع `fawakhry/TrendOs`. هذه المراجعة لا تثبت ما يعمل حاليًا على Production ولا تجري طلبات خارجية.

## الهدف

تأهيل اتصال صادر واحد من Ubuntu `TrendosShop` لقراءة أوردرات `print` و`laser` مع حساب خدمة محدود القراءة؛ لكل بند `lineId` مستقل ضمن أوردر `orderId` قد يتبع أكثر من قسم. عدم تعديل العميل أو المخزون أو الحسابات أو حالات التنفيذ.

## الحقائق المؤكدة في الكود

| الطبقة/الفرع | ما يظهر بالمصدر | النتيجة |
| --- | --- | --- |
| واجهة TrendOS الافتراضية `trendos-edge-orders-read-v1.js` | تبادل جلسة الموظف عبر `POST /v1/edge/orders/session` ثم تشير إلى `/v1/edge/orders/02cr/page` | مسار مستهدف في الواجهة، **ليس تأكيد Deploy** |
| كود `cloudflare-d1/src/edge-orders-read-v1.mjs` بفرع `candidate/t12-full-cloud-cutover-a56-20260929` | يقبل `POST /v1/edge/orders/session` و`GET /v1/edge/orders/page` فقط | عقد **مختلف بفرع أقدم** ولا يجوز افتراض أنه Production |
| نفس Worker الأقدم | `screensForRole('admin')` يعطي `service, print, laser, press, ''`؛ `print` يعطي `print, press, ''`؛ `laser` يعطي `laser, ''` | لا توجد في هذا المصدر صلاحية جاهزة لحساب واحد **print+laser فقط**؛ لا يعني ذلك غياب حل أحدث |

| `autonomous-printshop/print-server/src/trendos_client.py` | يرسل `POST /v1/employee/core` مع `action=getRows` | مسار قديم لا يثبت التوافق مع `getRowsPageV1931` أو Edge الحالية |

## ما أُثبت باختبارات GitHub من قبل

- [AP-299 run 38911533330](https://github.com/fawakhry/TrendOs/actions/runs/38911533330): 18 اختبار AP-299 + 17 اختبار AP-298 + 15 اختبار AP-296 = **50/50 PASS** على بيانات وهمية.
- اختبارات قسم واحد لا تعني أن المنتج محصور بالطباعة؛ الهدف متعدد الأقسام والخدمات.
- لم يُختبر الاتصال بحساب ضياء أو أي Secret حي، ولا تشغيل على الجهاز أو طابعات.

## بوابات لازمة قبل الاتصال الحقيقي

1. **G1 — عقد الخدمة المنشورة:** مراجعة نسخ الـWorker/route النشطة على Cloudflare في وضع قراءة فقط، وتعريف الـAPI الذي تستخدمه الواجهة الحية، وتوثيق إعادة التوجيه، الـpagination، schema، snapshot freshness وعزل الأقسام.
2. **G2 — الحساب والصلاحيات:** إعداد أو اختيار حساب خدمة مستقل **قراءة أوردرات الطباعة والليزر فقط** عبر تطبيق صلاحيات فعلية جهة السيرفر، من غير إدارة حسابات أو تعديل أوردرات. **حساب ضياء الإداري أو توكن تاريخي غير مناسب**. لا إنشاء حساب أو تغيير صلاحيات حي بدون موافقة صريحة.
3. **G3 — منفذ اتصال آمن:** تأهيل Client منفصل عن `run.py`، HTTPS صادر فقط مع عنوان موثوق ثابت وTLS محقق ورفض Redirects وفترة انتظار محددة وحد أقصى للبيانات وقراءة صفحة واحدة والتوقف. لا ملفات عملاء، لا طباعة ولا تعديل حالة.
4. **G4 — اختبار وهمي أولًا:** محاكاة `print` و`laser` و`401` و`403` والبيانات المختلطة والأوردر متعدد الأقسام. أي اختلاف عن عقد السيرفر الحقيقي يوقف التجربة.
5. **G5 — موافقة مستقلة على التجربة الحية:** طلب إذن منفصل من المالك لاستخدام حساب محدود وتجربة HTTPS واحدة؛ بيانات الدخول تبقى في مخزن أسرار مؤهل، ولا تُنسخ للشات أو السجل أو الـCI.

## الخطوة التالية المطلوبة من المالك

**قرار واحد فقط:** هل يوافق المالك على **تجهيز حساب خدمة تجريبي مستقل** يشاهد أوردرات `طباعة` و`ليزر` للقراءة فقط، دون صلاحيات إدارية أو كتابية؟ الموافقة على التخطيط لا تعني السماح بإنشاء الحساب الحي تلقائيًا، ولا استخدام بيانات العملاء.

3. ترتيب قوة الإثبات: **Runtime مُتحقق ومؤرخ لنفس البيئة > deployed مُثبت > اختبار دقيق على SHA > source-only > وصف تاريخي > UNKNOWN**. نتيجة CI ناجحة على commit قديم لا تساوي exact-HEAD PASS. `HTTP 200` وحده لا يثبت نجاح business path.
4. كل دليل اختبار يحمل `test_name, target_sha, workflow_run_url, run_conclusion, observed_at, scope, expected, actual, evidence_ref, book_entry, uncertainty`. الاختبار الذي لا يملك run/commit صالحًا يصنف `UNVERIFIED`، ولا تُكتب له PASS.
5. فهرس المصدر يحتاج لكل وحدة `path, sha, branch, owner/purpose, entrypoint, dependencies, data writer, tests, runtime authority, evidence, gaps, disposition`. عداد الملفات المكتشفة **لا يعني** أنها قُرئت أو اختُبرت.

## دورة كل تشغيل: PREPARE → READ → RECONCILE → DRAFT → VERIFY → RECORD
1. **PREPARE:** اختر **فجوة واحدة صغيرة** من قائمة الانتظار؛ سجل HEAD والنطاق وخطة القراءة ومعيار النجاح. لا تعيد عملًا موثقًا بدون سبب.
2. **READ:** اقرأ المصدر الأصلي والاختبار وسجل تشغيله وسجل الكتاب المرتبط، بما في ذلك الفشل السابق. لو كان النص غير متاح، `BLOCKED`.
3. **RECONCILE:** اسأل: هل الاختبار موثق بالفعل؟ هل نتيجته خاصة بآخر HEAD أم بكود سابق؟ هل نحتاج دليل نشر أو تشغيل مختلف؟ لا تضف سجلًا مكررًا.
4. **DRAFT:** حدث ملف queue/الفصل المرشح. التغيير المقترح على الكتاب الرئيسي يجب أن يكون append-only في سجل النتائج، أو تعديل قسم الحالة الحية بدليل أحدث مع الحفاظ على النسخ التاريخية في Git. لا إعادة كتابة جذرية تمسح التاريخ.
5. **VERIFY:** جلب مستقل للفرع والملف/المحتوى بعد commit، ثم تحقق من التوافق بين RUN/sha/status والرابط. إذا فشل الحفظ اكتب `UNKNOWN_OUTCOME` وامنع الاستمرار في الكتابة.
6. **RECORD:** سجل المختصر، commit، رقم PR، المواضع المحدّثة، `PASS|FAIL|BLOCKED|UNKNOWN` ونقطة الاستكمال. لا تصف فحص GitHub بأنه اختبار runtime.

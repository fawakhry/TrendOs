## 2026-09-20 further cross-account same-key guard

Found a replay-identity security and duplicate-order edge case during continued review: the initial isolated ledger prototype used a `keyDigest` of `[actor,requestKey]`, so a repeated globally unique client request key from another authenticated account could be interpreted as a NEW request and allocate a second business order. The legacy V1908 property mapping was keyed by requestKey globally, irrespective of the current actor. Also, replaying a saved response to an alternate actor can expose another account's order metadata. The isolated candidate now hashes **only the global request key** in `keyDigest`, and includes `actor` + canonical payload inside `payloadDigest`, ensuring that a second account using the same key produces `CONFLICT`, not `NEW` or `REPLAY`. This does not remediate the existing legacy V1908 cross-actor replay behavior; targeted deployed auth/routing review is still required before cutover.

Synthetic test `tests/t12_durable_order_replay_ledger_candidate.test.mjs` now checks global keyDigest equality across accounts, actor-bound payloadDigest inequality, lookup/reserve cross-account conflict, and exactly one existing ledger row. [Isolated GitHub Actions run 35519153107](https://github.com/fawakhry/TrendOs/actions/runs/35519153107), job 106100100114: **SUCCESS**. These fixtures do not test live production actors, real order/line writes, browser reloads, or actual Apps Script ledger performance.

**Cross-account deployment rule:** require a stable authenticated immutable actor ID or explicitly defined actor-identity lifecycle and verify frontend/backend principal normalization; never use a mutable display name blindly as a durable principal. For shared or transferred account identity, reconcile unknown history instead of treating the same key as a new request. Never weaken global key uniqueness to simplify a migration.

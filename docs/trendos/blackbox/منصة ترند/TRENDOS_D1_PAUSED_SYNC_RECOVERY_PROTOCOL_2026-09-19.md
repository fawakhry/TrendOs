## Code-review findings — do NOT invoke the existing start/tick methods as a shortcut

1. `cloudflare-d1/D1_Orders_Low_Usage_Control_V1.gs` `startD1OrdersLowUsageSyncV1()` calls `d1OrdersLiveSyncV2ClearBaseline_()`, then `d1OrdersLiveSyncTickV2()`, then creates the recurring trigger. It **intentionally forces a full initial sync** and clears the existing trusted baseline; this is NOT a safe one-shot delta recovery entrypoint.
2. `cloudflare-d1/D1_Orders_Live_Sync_V2.gs` `d1OrdersLiveSyncTickV2()` runs a **full atomic rebase** when baseline absent or last full sync is **24 h old**; this branch writes multiple D1 stage chunks and rewrites local baseline metadata. A manually run V2 tick is not guaranteed to stay delta-only. The previous full-sync timestamp was `2026-09-19T14:13:49.388Z` in the owner's local metadata audit; age must be re-evaluated at actual execution, not inferred from this report.
3. `d1OrdersLiveSyncV2ComputeDelta_()` calculates source-vs-**local baseline** row hashes. The worker's `cloudflare-d1/src/mirror-delta-gate.mjs` delta preflight checks ready/catalog row counts, contiguous rows and expected note, **not exact per-row equality with that local baseline**. Therefore matching catalog counts alone cannot certify that applying baseline-derived changed rows preserves all D1 content. If D1 already diverged from local baseline, a narrow delta could leave older wrong rows untouched.
4. The live V1908 replay properties still occupy ~346205 measured bytes in the post-cleanup audit. New order traffic can consume Script Properties again; restoring high-frequency tasks without an idempotency-preserving storage/retention strategy risks quota recurrence. Do not describe the one-time cleanup as a permanent fix.
5. The separate operational enrichment job has its **own** baseline/full-sync policy and must not be resumed merely because Orders/Lines recovery succeeds.

**G1 — mirror lineage, read-only:** At the time of planning, compare the stored **V2 local baseline to the actual D1 mirror rows**, not merely to the source Sheet or D1 catalog. For both tabs, verify workbook identity, matching sheet IDs, row numbers, source dimensions, headers, ready status, expected note, exactly one catalog row per tab, complete paginated GET coverage, exact row-hash agreement for all baseline rows, and stable D1 catalog metadata before/after pagination. Report only counts and statuses; keep all raw remote row contents, local baseline hashes, names/IDs, customer data, endpoint and secret out of logs/chat/GitHub. If baseline-vs-D1 does not match exactly, **stop**; plan a separately approved, bounded atomic rebase with dedicated quota assessment, not a baseline-derived partial delta. A catalog count match alone is insufficient.

**G2 — fresh source & quota preflight:** Capture the authoritative two source tabs while holding the same Script Lock used for order-create; check current source-vs-baseline hash delta and no unsafe truncations/reorders, bound total changed/new rows and expected D1 write size to separately reviewed limits (the previous 159 is NOT a hardcoded cap or current count); inspect actual current Script Properties count/bytes, projected baseline chunk count and largest per-value size, quotas and fresh errors. Do not rely solely on approximate key+value totals to claim guaranteed headroom. If 24-hour full rebase is due, or any preflight fails, **abort with no D1 or property write**; never fall through to the ordinary V2 full-sync path. Inspect whether live create-order calls share that lock and whether external Sheet edits can race, and treat any source drift during the operation as pending additional work rather than automatically retrying.

**G3 — proposed ONE-TIME delta ONLY, approval required:** Design and mock-test a dedicated manual, fail-closed helper that cannot create triggers, enable flags, clear the baseline, silently choose full rebase, access archived/private backups, or touch auth/order counters. Demand explicit approval before production execution. Immediately before any mutation, revalidate G1/G2 against current data; submit only verified changed/new source rows for both tabs through the established atomic D1 delta endpoint. The endpoint's catalog/contiguity preflight is helpful but not a substitute for G1. Never send two independent writes that could expose mixed Orders and Lines versions. After a reported D1 success, verify the actual remote row-content snapshot against the captured source before replacing the local baseline; evaluate failure cases in which the D1 commit succeeds but Apps Script times out or property write fails. **Never blindly rerun after ambiguous timeout**, reconcile via GET first.

**G4 — separate verification and future automation gate:** Log sanitized one-time run receipt, fresh quota audit, original-sheet vs D1 read parity, and any source rows edited after the capture; keep automatic triggers paused until stable mirror freshness and a safe quota/idempotency retention strategy have been independently validated.

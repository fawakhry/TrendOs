Date: 2026-10-10 | Branch: `feat/acc175-strict-authenticated-finance-grants-20261010`

## Identified G2 structural release blocker
Server `accountingMode(user)` presently uses verified cloud session `user.username`, role and department plus substring/nickname heuristics. The session is verified; the issue is the **lack of explicit owner-approved permission grants** and the possibility of role inference from a name/department substring. Owner mapping, not another synthetic test, is still required to pass [permission release issue #40](https://github.com/fawakhry/TrendOs/issues/40).

## Implemented narrow source change
- `cloudflare-d1/src/employee-accounting-native-v1.mjs` introduces `approvedAccountingModeV1(env,verifiedUsername,user)` and calls it after the cloud-first `verifyEmployeeSessionCloudFirst` verified the session.
- **Default completely unchanged:** if server-only `ACCOUNTING_FINANCE_GRANTS_MODE_V1` is absent/empty, existing `accountingMode(user)` is used to preserve current staff access until owner-approved transition. This is NOT approval for any production finance write.
- When the owner later explicitly configures server-only `ACCOUNTING_FINANCE_GRANTS_MODE_V1=ENFORCE`, the separate server-only `ACCOUNTING_FINANCE_GRANTS_V1` must contain JSON `{"version":1,"grants":[{"username":"<approved authenticated login>","mode":"print"}]}`. Other allowed `mode` values are `full`, `final`, `laser`. This example is schema illustration only, **not a real employee mapping**.
- Strict path maps the **exact normalized authenticated identifier returned by the verified cloud session**, never a username, role or department from untrusted request body; denies absent matched grant, absent trusted session identity, bad JSON/version/type, wildcard user, duplicate normalized username, unsupported mode/extra fields, missing roster or unexpected gate mode. Full failure returns 403, never falls back to legacy heuristic once enforce is selected.
- The `username` identity used in the strict resolver comes only from `v.body.user.username`, `v.body.user.name` or `v.body.username` in the verified session response. Client-supplied username remains a verifier input for session validation but **cannot supply a missing strict verified principal**.
- Existing `READONLY` blocks every non-read action before authentication. This is a policy feature guarded by server-only ENV and **has not been activated/deployed**. No production worker config, staff accounts or existing employee permissions changed.

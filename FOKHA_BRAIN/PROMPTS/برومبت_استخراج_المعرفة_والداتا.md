# برومبت استخراج المعرفة والداتا — عقل فوخا

## المهمة

اقرأ المصدر المطلوب كاملًا بقدر الإمكان، واستخرج منه **كل معرفة أو داتا يمكن الاستفادة منها لاحقًا** في الإدارة، اتخاذ القرار، تشغيل المشاريع، التعلم، الأتمتة، تحسين الجودة، تقليل الأخطاء، أو بناء أنظمة أذكى.

لا تتعامل مع المصدر كملخص نصي فقط. تعامل معه كـ **منجم معرفة**.

## مصادر يمكن التحليل منها

- محادثات ChatGPT / Gemini / أي AI.
- GitHub code, docs, commits, issues, checkpoints.
- Google Sheets / Docs / Drive.
- ملفات تشغيل أو تقارير.
- قرارات المستخدم.
- نتائج تجارب وفشل ونجاح.
- بيانات تشغيلية أو مالية موثقة.
- إجراءات عمل متكررة.
- أكواد تكشف عن قواعد فعلية في النظام.

## استخرج الأنواع التالية

### 1. Facts / Data
حقائق صريحة وأرقام وأسماء وحالات ومواعيد ومعرّفات وروابط وعلاقات بين الكيانات.

### 2. Decisions
أي قرار اتخذه المستخدم أو تم اعتماده صراحة، مع السياق والسبب إن وجد.

### 3. Rules
قواعد ثابتة أو شبه ثابتة ظهرت في كلام المستخدم أو في طريقة بناء النظام.

### 4. Thinking Patterns
أنماط اتخاذ القرار، ترتيب الأولويات، التعامل مع المخاطر، السرعة مقابل الدقة، الأتمتة، الجودة، التفويض، التحقق، والـrollback.

### 5. Workflow Knowledge
خطوات تشغيل تتكرر ويمكن تحويلها إلى SOP أو Automation أو Checklist.

### 6. Project Knowledge
معرفة تخص مشروعًا بعينه ولا يجوز تعميمها تلقائيًا على كل مشاريع فوخا.

### 7. Reusable Business Knowledge
خبرة قابلة لإعادة الاستخدام في مشاريع أخرى: تسعير، تشغيل، جودة، خدمة عملاء، موردين، إنتاج، تصميم، متابعة، محاسبة، بنية تقنية، إلخ.

### 8. Negative Learning
أخطاء، فشل، طرق لم تنجح، اختناقات، أسباب رفض، regression، مخاطر، أو ممارسات يجب تجنبها.

### 9. Opportunities / Ideas
أفكار أو فرص تحسين أو منتجات أو أتمتة أو ربط بين أجزاء النظام.

### 10. Relationships / Linking
استخرج كل علاقة مفيدة مثل:
`Order ID <-> Line ID <-> Case ID <-> Asset ID <-> Knowledge ID`
أو أي ربط بين مشروع وملف وقرار وقاعدة ومهمة.

### 11. Standards / Constraints
أي حدود أو شروط لا يجب كسرها: أمان، صلاحيات، جودة، خصوصية، مصدر حقيقة، مفاتيح ربط، تنسيق، SLA، بوابات قبول.

### 12. Open Questions / Unknowns
أي شيء ناقص أو متعارض أو يحتاج تحققًا لاحقًا. لا تملأ الفراغ بالتخمين.

## التمييز الإجباري

كل عنصر مستخرج يجب تصنيفه كواحد من:

- `EXPLICIT_USER` — قاله المستخدم صراحة.
- `VERIFIED_SOURCE` — مثبت في كود/ملف/Runtime evidence.
- `INFERRED_PATTERN` — استنتاج من نمط متكرر ويحتاج درجة ثقة.
- `AI_SUGGESTION` — اقتراح AI وليس قرارًا.
- `UNKNOWN / NEEDS_VERIFICATION` — غير محسوم.

## قاعدة الثقة

- `HIGH` عندما يكون صريحًا أو مدعومًا بأكثر من دليل قوي.
- `MEDIUM` عندما يكون استنتاجًا قويًا لكنه غير مصرح به مباشرة.
- `LOW` عندما يكون مجرد إشارة أو يحتاج تحققًا واضحًا.

## قاعدة عدم التعميم

لا تحول:
- تفضيل عميل واحد إلى قاعدة عامة.
- فشل حالة واحدة إلى قانون مطلق.
- رأي AI إلى قرار مستخدم.
- كود قديم إلى حقيقة Production حالية.

## قاعدة المصدر

احتفظ قدر الإمكان بـ:

- `source_type`
- `source_name`
- `repo/file/path`
- `commit/branch/version`
- `chat/date`
- `project`
- `related_ids`

## قاعدة الحقيقة

عند التعارض استخدم هذا الترتيب ما لم يحدد المشروع ترتيبًا أدق:

`LATEST VERIFIED > EARLIER VERIFIED > DEPLOYED > TESTED > IMPLEMENTED > PREPARED > PLANNED > UNKNOWN`

ولا تعتبر الخطة تنفيذًا، ولا التنفيذ تحققًا، ولا CI نجاحًا في Production بدون Runtime Evidence عندما تكون الحقيقة تشغيلية.

## بعد الاستخراج

صنّف كل عنصر إلى أحد المسارات التالية:

- `FOKHA_GLOBAL` — قاعدة أو معرفة عامة تخص عقل فوخا.
- `PROJECT_MEMORY` — تخص مشروعًا بعينه ويجب أن تبقى في ذاكرته الرسمية.
- `CANDIDATE_RULE` — قاعدة محتملة تحتاج تكرار/تأكيد.
- `DECISION_LOG` — قرار صريح.
- `IDEA_INBOX` — فكرة غير ناضجة بعد.
- `NEGATIVE_LEARNING` — فشل أو نمط يجب تجنبه.
- `DATA_REFERENCE` — داتا مفيدة لكن مصدر الحقيقة يبقى خارجيًا.

## أهم قاعدة

**استخرج ما يمكن الاستفادة منه، وليس ما يمكن نسخه فقط.**

الهدف ليس تكبير الذاكرة، بل جعل كل محادثة وكل مشروع وكل تجربة تزيد قدرة عقل فوخا على الفهم، الربط، اتخاذ القرار، واختصار وقت المستخدم في المستقبل.
